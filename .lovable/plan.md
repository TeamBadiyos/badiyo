# Multi-stop parcel: backend phase (no UI changes)

Current parcel and shop delivery bookings keep the same prices and the same flow. Multi-stop stays switched off in practice because every rate still allows only 1 pickup and 1 drop.

## What changes
1. **Price quote knows the stop count.** It takes the number of pickups and drops (both default to 1). It turns down counts below 1 or above the rate's limits, with "Maximum X pickups allowed" / "Maximum X drops allowed". The stops fee is extra pickup fee × (pickups − 1) + extra drop fee × (drops − 1). It is added after the distance price, next to the vehicle-type extra and platform fee. Coupon, GST and total are worked out the same way as today. For 1 pickup and 1 drop the stops fee is 0, so the result is the same as today.
2. **Route planner.** A new helper puts stops in route order: the first pickup stays first, the other pickups follow nearest-next, then the drops follow nearest-next starting from the last pickup. It only calculates and never saves anything.
3. **Distance check.** A new helper adds up the straight-line distance between the stops in order. An order is refused with "DISTANCE_MISMATCH" if the distance sent is below 95% of that figure minus 0.2 km. This applies to both single and multi-stop orders.
4. **Multi-stop order creation.** If an order includes a stops list, the new path runs. Otherwise the current path runs unchanged, plus the distance check. The new path checks all the rules in your brief (a to g), gets the quote, saves the order, then saves all its stops and parcels together. If any step fails, nothing is saved.
5. **App server layer.** The quote accepts an optional pickup count and drop count. Order creation passes stops and parcels through unchanged. A new call exposes the route planner.

## Technical details
- Read the current `courier_quote_internal`, `courier_create_order`, `courier_validate_local_route` and `haversine_km`, plus every caller of the quote: `store_courier_fare`, `store_create_courier_job` and the server fn. The quote gets two trailing params with `DEFAULT 1`. If the signature changes, the old overload is dropped in the same migration so named and positional callers still resolve. Grants are re-applied as they are today (service_role; no anon).
- The jsonb result gains `pickup_count`, `drop_count` and `stops_fee`. All existing keys and rounding stay the same. The km value is never rounded. `min_fare` only applies to the distance part.
- `courier_plan_stops(jsonb)` and `courier_min_route_km(jsonb)`: IMMUTABLE/STABLE SQL/plpgsql. Execute is granted to authenticated and service_role.
- Multi-stop path: validations run first, then `set_config('app.courier_skip_default_stops','on',true)`. Next, the order is inserted with the flat pickup/drop fields set to the first pickup and first drop, plus `pickup_count`, `drop_count`, `stops_fee` and `fare_breakdown`. Then `courier_order_stops` rows (sequence 1..n) and `courier_order_parcels` rows are inserted, with keys mapped to the new stop ids. The return value is the current shape plus a `stop_ids` map. Phones are checked with the same 10-digit Indian mobile rule the current create path uses.
- `src/lib/courier.functions.ts`: add optional `pickup_count` and `drop_count` to `quoteSchema`, and optional `stops` and `parcels` to `createSchema`, passed into `_payload`. Add a new `courierPlanStops` server fn. The distance for multi-stop orders is still calculated on the server.
- Razorpay amount: it already comes from the server (`courier_orders.total_amount` returned by `courier_create_order`, and `create-razorpay-order` for the courier purpose). This is checked in both places, and any other source is reported without being changed.
